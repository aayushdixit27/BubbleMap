# Field guides

Not session reading. Open one when the situation it covers actually arrives.

Each file was produced the same way: take a body of published thinking, **run it live
against a real constraint this project was facing**, and keep only the parts that
changed a decision. Everything that sounded good and did no work is listed at the end
of each file, so a reader can see it was considered rather than missed.

| file | about | use it when |
|---|---|---|
| `strategy_that_worked.md` | Deciding — diagnosis, crux, inputs vs outputs | You're about to optimise something, or you can't tell which of two things to do first |
| `standards_that_worked.md` | Holding a standard while building | Output quality is drifting, or you're about to ship something you haven't looked at |
| `systems_that_worked.md` | The machine you're standing inside | Work is queueing, something is silently failing, or you suspect you're the bottleneck |

**Hit rates: 5, 7 and 6 of roughly eighteen concepts each.** That's the honest yield
and it's worth expecting — the value of a framework is not that all of it applies,
it's that you can find the useful sixth of it quickly.

**Reading them all at once is the wrong use.** They overlap deliberately (all three
arrive at "steer by inputs you control" from different directions), and read together
they blur into advice. Read singly, against a live problem, they decide things.

## The method, if you want to make another

1. Have a real, current, unresolved constraint. Not a hypothetical.
2. Run the framework's concepts against it one at a time. Most will do nothing.
3. Keep only those that **changed a decision**, and write the worked example — the
   specific thing that was going to happen and then didn't.
4. List what didn't fire, by name.
5. Report the hit rate honestly. A framework that fires on everything is a horoscope.
6. End with live recommendations, so the file is a tool rather than a retrospective.
